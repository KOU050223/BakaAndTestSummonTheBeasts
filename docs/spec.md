## 1. プロダクト概要

### 1.1 プロダクトビジョン

「試験召喚システム」は、ライトノベル・アニメ「バカとテストと召喚獣」の世界観を実際の学校教育に組み込み、生徒の学習意欲を向上させる教育支援プラットフォームです。試験の成績データをもとに召喚獣を生成・育成し、クラス対抗戦（試召戦争）を通じて生徒が楽しみながら学べる環境を提供します。

> **最終目標：試験召喚システムを学校に導入できるまで持っていきたい**

### 1.2 MVP（最小実用プロダクト）スコープ

まず以下のコア機能を優先して開発します。MVPの成功条件は、教師が試験を登録して点数を手動入力し、生徒が自分の点数と召喚獣ステータスを確認できることです。

- 採点システム（試験結果のデジタル化）
- 生徒への点数フィードバック（FB）機能
- 召喚獣ステータス表示
- 1対1のシンプルなターン制バトル

### 1.3 将来の発展スコープ

- OCR・AI採点による採点支援
- 試召戦争システム（クラス対抗バトル）
- 3Dフィールド上での交流・召喚演出
- クラス設備攻略
- 勉強周り支援機能（学習計画・コンテンツ連携）

## 3. 機能仕様

### 3.1 試験・採点システム（MVP）

試験結果をデジタルデータとして蓄積し、召喚獣のパラメータや生徒へのフィードバックに活用する中核機能です。

#### 3.1.1 試験作成フロー

1. 教師または学校管理者が生徒・クラスを事前登録する
2. 教師が科目・対象クラス・満点を指定して試験を登録する
3. 教師が採点済み答案をもとに点数を手動入力する
4. システムが生徒の召喚獣ステータスを再計算する
5. 生徒が点数と召喚獣ステータスを確認する

入学試験によるクラス振り分けは将来スコープとし、MVPでは既存クラスへの所属を前提にします。

#### 3.1.2 採点データの入力方式

| フェーズ | 方式 | 内容 |
|---|---|---|
| フェーズ1（MVP） | 手動入力 | 教師が採点済み答案の点数を手動入力 |
| フェーズ2 | OCR | 答案または採点結果の読み取り支援 |
| フェーズ3 | AI自動採点 | AIによる採点・入力支援（人間がデータチェック・修正） |

MVPではOCRとAI自動採点は実装しません。まず手動入力で成績データの登録・確認・ステータス反映の流れを完成させます。

#### 3.1.3 対応科目

- MVP対応: 英語、数学、物理、化学、生物、地学、地理、日本史、世界史、現代社会、国語
- 各試験は1科目・100点満点を基本とする
- 満点は試験ごとに設定できるが、召喚獣ステータス計算では100点換算する
- 総合科目はMVP対象外とする

総合科目の点数配分は将来スコープで定義します。コンピューター関係の比重を含む複合評価は、通常科目の成績管理が安定してから扱います。

#### 3.1.4 生徒へのフィードバック

- 採点後、各生徒に点数をフィードバック
- 生徒は自分の点数、対象科目、試験名、登録日を確認できる
- 生徒は点数に基づいて再計算された召喚獣ステータスを確認できる
- 教師はクラス単位で登録済み点数を確認できる
- 教内テストへの回答支援機能（OMCアイキャッチ形式での回答）は将来スコープとする
- 継続的な学習促進の仕組みは、MVPでは召喚獣ステータスの変化を見せることに限定する

---

### 3.2 召喚獣システム

生徒の試験成績をもとに召喚獣を生成し、成長・強化させるゲーミフィケーション要素です。
召喚した召喚獣を元に対戦を行います。召喚獣のステータスはテストの点数が反映されます。

#### 3.2.1 召喚方法

MVPでは音声認識による召喚は実装せず、生徒画面またはバトル画面で召喚獣を表示します。SpeechRecognition APIを使った起動ワード検知は将来スコープです。

> **起動ワード：「試験召喚獣召喚・試獣召喚（サモン）！」**（原作：バカとテストと召喚獣 準拠）

#### 3.2.2 召喚獣パラメータ

- 各科目の最新点数に応じて召喚獣の強さが決まる
- 点数は100点換算し、HP・攻撃・防御・素早さへ変換する
- 成績向上により召喚獣ステータスが上がる
- 召喚獣の強さは1対1バトルの結果に影響する
- MVPでは見た目の進化、装備、スキルツリーは扱わない

MVPのステータス計算はRailsで行い、PostgreSQLに保存された点数を正本とします。具体的な計算式は実装時に単純な一次式から開始し、ゲームバランス調整は後続フェーズで行います。

---

### 3.3 試召戦争システム

クラス対抗・個人対抗のバトル機能です。生徒の学習意欲向上を主な目的とします。MVPでは個人対個人の1対1ターン制バトルのみを扱い、クラス対抗戦は将来スコープとします。

#### 3.3.1 バトル開始フロー

1. 教師またはシステムが対戦科目と2人のプレイヤーを指定してバトルを作成する
2. React Battle UIがGo Game ServerのWebSocketへ接続する
3. Go Game ServerがRails APIからバトル開始データを取得する
4. プレイヤーがボタン操作で行動を選択する
5. Go Game ServerがHP・ターン・行動・フェーズを同期する
6. どちらかのHPが0になったらバトルを終了する
7. Go Game ServerがRails APIへ結果を保存する
8. React Battle UIがリザルトを表示する

宣戦布告、リーダー指定、クラス設備攻略への反映はMVPでは実装しません。

#### 3.3.2 バトルルール

| 項目 | MVP仕様 |
|---|---|
| 対戦形式 | 1対1 |
| 対戦科目 | バトル作成時に指定した科目で実施 |
| バトル操作 | ボタン操作によるシンプルな戦闘UI（ボタンぽちぽちで完結） |
| 行動 | MVPでは通常攻撃のみ |
| 戦闘の流れ | ターン制。行動選択後にダメージ計算し、HPを同期する |
| 逃げる選択肢 | MVPでは実装しない |
| リーダー指定 | MVPでは実装しない |
| 勝敗条件 | 相手のHPを0にしたプレイヤーが勝利 |

逃げる、スキル、属性、チーム戦、複雑なマッチングは後続フェーズで検討します。

#### 3.3.3 3Dフィールド（将来構想）

- 3Dフィールド上にキャラクターをバラバラに配置
- フィールド上でバトルモードに入る仕組み
- 戦える・友だちと交流できる空間
- バトル終了後、3Dフィールドの適切なビューへ戻る

> 「なるべくみんなが解るよう思慮したい」—— アクセシビリティ・わかりやすさを重視した設計方針。

## 4. システムアーキテクチャ

### 4.1 技術スタック

2週間MVPでは、採点・成績管理とリアルタイム対戦を分離し、以下の構成を採用方針とします。

```txt
Frontend:
  React + Vite + TypeScript

REST Backend:
  Ruby on Rails API mode + PostgreSQL

Realtime Game:
  Go + WebSocket

Auth:
  Rails JWT

Deploy:
  Cloud Run
```

#### 4.1.1 採用方針

「Rails REST API + Go Game Server」を採用します。ただし上級者向け構成のため、MVPでは以下の条件を守ります。

- Railsは成績・ユーザー・試験管理に限定する
- Goはゲーム中のリアルタイム処理に限定する
- RailsとGoを密結合させない
- 最初は1対1バトルだけにする
- 3Dワールドの本格的な位置同期はMVPから外す

#### 4.1.2 責務分離

| 領域 | 役割 | 主な責務 |
|---|---|---|
| React Frontend | ユーザー操作・表示 | 教師UI、生徒UI、召喚獣ステータス表示、バトルUI |
| Rails REST API | 永続データの正本 | ユーザー管理、教師・生徒管理、クラス管理、試験管理、点数入力、召喚獣ステータス計算、バトル履歴保存 |
| Go Game Server | 対戦中の一時状態管理 | WebSocket接続、マッチング、バトルルーム管理、ターン処理、HP同期、勝敗判定、バトル結果通知 |
| PostgreSQL | 永続化 | 学校・クラス・ユーザー・試験・点数・召喚獣・バトル履歴 |

Railsを永続データの正本とし、DBマイグレーションとDB接続はRailsバックエンドが一任します。GoはPostgreSQLを直接操作せず、必要なデータ取得・結果保存はRails API経由で行います。

```txt
[React Frontend]
  |
  | REST
  v
[Rails API]
  |
  | PostgreSQL
  v
[DB]

[React Battle UI]
  |
  | WebSocket
  v
[Go Game Server]
  |
  | battle result POST
  v
[Rails API]
  |
  v
[PostgreSQL]
```

#### 4.1.3 API設計

Rails REST API、Rails-Go間のinternal API、Go Game ServerのWebSocket APIの詳細は [API詳細設計](./apiSpec.md) に分離します。

#### 4.1.4 MVPでやること・やらないこと

やること:

- Railsでユーザー・クラス・試験・成績管理APIを作る
- Railsで召喚獣ステータスを計算する
- Goで1対1バトルWebSocketを作る
- Goはメモリ上でバトル状態を管理する
- バトル終了時にRailsへ結果を保存する
- Reactで教師UI・生徒UI・バトルUIを作る

やらないこと:

- GoからDBを直接操作する
- 本格的な3D位置同期を行う
- 物理演算バトルを行う
- 複雑なマッチングを行う
- 多人数同時戦争を行う
- OCR・AI採点を行う
- SpeechRecognition APIによる召喚を行う
- 総合科目の複合評価を行う
- クラス設備攻略を行う

#### 4.1.5 開発分担案

| 担当 | 役割 |
|---|---|
| 上級生A | Rails / DB / API |
| 上級生B | Go / WebSocket / Battle |
| 初心者A | 教師UI |
| 初心者B | 生徒UI / バトルUI |

#### 4.1.6 デプロイ案

| 領域 | 候補 |
|---|---|
| Frontend | Vercel |
| Rails API | Cloud Run |
| Go Game Server | Cloud Run |
| DB | Cloud SQL for PostgreSQL |

GCP運用に詰まる場合のみ、Render / Railway / Fly.io / Supabase Postgres / Neon を代替候補として検討します。

### 4.2 データフロー概要

1. 教師が試験を実施・採点する
2. 採点データをシステムに登録
3. 生徒の召喚獣パラメータを更新
4. 生徒に点数フィードバックを通知
5. 1対1バトル時、最新パラメータでバトル処理を実行

## 6. 後続検討事項

### 6.1 MVP後に検証する技術

- OCR精度と採用ライブラリ

- 総合科目の点数配分ルール
- クラス設備攻略の仕様

- 教師向けオンボーディング手順

- 生徒・保護者への説明方針
- 本番運用時の障害対応・バックアップ方針
